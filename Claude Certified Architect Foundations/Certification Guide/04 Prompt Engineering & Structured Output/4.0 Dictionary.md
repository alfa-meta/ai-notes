# Domain 04 Dictionary — Prompt Engineering & Structured Output

**"other" + detail string** — Schema pattern pairing an `"other"` enum value with a freeform detail field, to capture edge cases predefined categories don't cover.

**"unclear" enum value** — Explicit enum option for genuinely ambiguous source material, preventing the model from forcing a false classification.

**Attention dilution (review)** — Inconsistent review depth across a large multi-file input; fixed by multi-pass architecture (per-file + integration pass), not a bigger context window.

**Batch failure handling** — Correct pattern: identify failures by `custom_id`, resubmit only the failures (with modifications like chunking or added examples), and refine prompts on a sample set beforehand.

**Calibrated confidence threshold** — A confidence cutoff validated against labelled data (vs raw/uncalibrated self-reported confidence), suitable for automated routing decisions.

**calculated_total vs stated_total** — Self-correction schema pattern: extract both the model's summed total and the document's stated total; a mismatch is an automatic discrepancy flag needing no external logic.

**Confidence-based filtering** — Anti-pattern of only reporting "high-confidence" findings; fails because LLM self-reported confidence is poorly calibrated. Explicit criteria come first, confidence-based routing second.

**Confidence-based routing** — Routing high-confidence findings to developers directly and low-confidence findings to human review, using confidence scores calibrated against labelled data.

**conflict_detected boolean** — Schema field flagging when a source document contains contradictory information, so the model reports both values instead of silently picking one.

**custom_id** — Unique identifier on each Message Batches API request, used to correlate it with its response and to target resubmission of only the failed items.

**detected_pattern field** — Structured finding field recording which specific code construct triggered it, enabling analysis of dismissal patterns to guide prompt refinement.

**Explicit categorical criteria** — Concrete rules defining exactly what to flag and what to skip (vs vague instructions like "be conservative"); the correct fix for false-positive-prone prompts.

**False positive trust problem** — High false positives in one finding category destroy developer trust in ALL categories, even accurate ones; fix is to temporarily disable the broken category while reworking it, not abandon it.

**Few-shot prompting** — The most effective technique for consistent, well-formatted output; 2-4 targeted examples that include reasoning, deployed when instructions alone produce inconsistent formatting, judgement, or extraction.

**Format normalisation rules** — Formatting-consistency instructions included in the prompt alongside the schema; the schema enforces structure, the prompt enforces formatting consistency — the two work together, neither alone is enough.

**Hallucination reduction effect** — Side effect of few-shot examples: showing varied document structures teaches the model to handle structural variety without inventing data.

**Independent review instance** — A separate Claude invocation with no access to the generation session's reasoning context; catches issues a same-session self-review misses.

**Message Batches API** — 50% cheaper than synchronous calls, up to 24hr processing with no latency SLA, no multi-turn tool calling mid-request; for latency-tolerant workflows only.

**Multi-pass review architecture** — Splitting a large review into per-file local analysis passes plus a separate cross-file integration pass, to prevent attention dilution.

**Optional/nullable fields** — Schema design that lets the model honestly return null instead of fabricating a value when source information is absent — the primary defence against fabrication.

**Pydantic** — Python validation layer that enforces both structure (types, required fields) and semantics (custom validators, e.g. cross-field sum checks), producing the specific per-field errors a retry loop needs.

**Prompt-based JSON** — Asking the model to output JSON in a plain text response, with no structural guarantees; the inferior alternative at the bottom of the reliability hierarchy, below `tool_use` with JSON schemas.

**Retry effectiveness boundary** — Retries fix format mismatches, structural errors, and math errors; they cannot conjure information genuinely absent from the source document — that needs human review.

**Retry-with-error-feedback** — Correct retry pattern: resend the original document, the failed extraction, and the specific validation error together.

**Self-review limitation** — A model retains its own generation reasoning and is biased to confirm rather than challenge it when reviewing its own output in the same session.

**Semantic errors vs syntax errors** — `tool_use` with JSON schemas eliminates syntax errors (malformed JSON) but not semantic errors (wrong sums, misplaced values, fabricated data), which need separate validation logic.

**Sample set testing** — Refining extraction prompts against 5-10 representative documents before submitting a full batch, to maximise first-pass success and minimise costly resubmissions.

**Severity calibration** — Defining severity levels (critical/minor) using concrete code examples rather than prose descriptions, for consistent classification.

**SLA calculation (batch)** — Working backwards from a total SLA minus the batch API's 24hr max processing window to determine submission frequency/buffer.

**The Matching Rule** — Blocking, latency-sensitive workflows (pre-merge checks, real-time review) must stay on the synchronous API; only latency-tolerant workflows (overnight reports, weekly audits) should move to the Message Batches API.

**tool_choice** — Parameter with three modes: `"auto"` (may skip tool call), `"any"` (must call some tool, guaranteed structured output), or a forced named tool (mandatory specific step).

**tool_use with JSON schemas** — The top of the structured-output reliability hierarchy; the tool's schema constrains Claude's output shape, eliminating JSON syntax errors entirely.

**ValidationError** — Pydantic's exception surfacing both parsing and validator failures as machine-readable, per-field error messages.
