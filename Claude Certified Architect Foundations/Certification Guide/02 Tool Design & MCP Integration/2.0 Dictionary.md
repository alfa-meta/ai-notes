# Domain 02 Dictionary — Tool Design & MCP Integration

**.mcp.json** — Project-level MCP server config file at the repo root; version-controlled and shared with the whole team via git.

**~/.claude.json** — User-level MCP server config in the home directory; personal, not version-controlled, not shared.

**Access failure vs Valid empty result** — Critical distinction: an access failure means the tool couldn't reach the data source (retry may help); a valid empty result means the query ran successfully and found nothing (never retry).

**Barrel file** — A re-export module; when tracing function usage, you must also Grep for the barrel file's module name to catch consumers who import through it.

**Build-vs-Use decision** — Whether to build a custom MCP server or use an existing community one. Exam default: evaluate community servers (Jira, GitHub, Slack, etc.) first; build custom only for team-specific workflows they can't handle.

**Business error** — Error category for policy violations or business rule conflicts (e.g. refund exceeds limit); technically valid request, `isRetryable: false`, needs an alternative workflow such as escalation.

**Edit (tool)** — Built-in tool for targeted file modification via unique text matching (`old_string`/`new_string`); fails on non-unique matches — widen the anchor or use `replace_all` before falling back to Read+Write.

**Environment variable expansion** — `${VARIABLE_NAME}` syntax in `.mcp.json` that keeps credentials out of version control while still sharing server config.

**errorCategory** — Structured metadata field classifying a tool failure as transient, validation, business, or permission.

**Glob** — Built-in tool that matches file PATHS by naming pattern (e.g. `**/*.test.tsx`); does not search file contents.

**Grep** — Built-in tool that searches file CONTENTS for patterns (function calls, error messages, imports); does not match file paths.

**Incremental codebase understanding** — Correct exploration strategy: Grep to find entry points → Read to trace flows → Grep again to trace usage, rather than reading all files upfront.

**isError** — MCP protocol flag that signals a tool call failed, letting the model reason about recovery instead of treating error text as a normal result.

**isRetryable** — Structured error field answering "can a retry ever succeed?" True for transient/validation errors, false for business/permission errors.

**Least privilege (tool design)** — Principle of giving each tool/agent exactly the capability it needs and nothing more (e.g. a constrained `load_document` instead of a generic `fetch_url`).

**Local recovery with selective propagation** — Multi-agent error-handling principle: subagents retry transient failures locally first, and only propagate errors (with partial results and what was attempted) that they can't resolve themselves.

**MCP Resources** — Content catalogues (issue summaries, doc hierarchies, DB schemas) an MCP server exposes upfront, so agents don't burn tool calls on exploratory discovery.

**MCP Server** — A program that exposes tools, resources, and prompts to an AI through the Model Context Protocol.

**Misrouting** — When overlapping/near-identical tool descriptions cause an agent to select the wrong tool; for a small toolkit, the fix is to expand/sharpen descriptions (not add few-shot examples or a routing classifier) — but at large tool counts (e.g. 22 near-duplicate tools) the same symptom means the toolkit needs consolidating, not better wording.

**MCP tool description sparseness** — A sparsely-described MCP tool loses out to built-in tools (like Grep) even when more capable, because the model has richer context about built-ins; fix by writing detailed MCP descriptions that explain capabilities and outputs fully.

**Model Context Protocol (MCP)** — Open standard defining how AI applications connect to external tools, data sources, and systems via a Host/Client/Server architecture.

**Permission error** — Error category for access denied / insufficient credentials; `isRetryable: false`, needs escalation or different credentials.

**Read / Write** — Built-in tools that load/write an entire file; the last-resort fallback for modifications when Edit can't disambiguate a unique anchor.

**replace_all** — Edit tool parameter that updates every occurrence of `old_string`, used when a non-unique match is intentional.

**Scoped cross-role tool** — A constrained version of another role's capability given directly to an agent for high-frequency simple operations (e.g. `verify_fact` on a synthesis agent), avoiding coordinator round-trip latency.

**Tool consolidation** — Collapsing many near-duplicate tools that share one shape (data in, operation, data out) into a single parameterised tool with an enum (e.g. 19 transformation tools → one `transform_data` tool). The correct fix when tool count itself is the problem, not description quality — unlike sharpening descriptions, which only helps small toolkits.

**Tool description** — The primary (not supplementary) mechanism LLMs use for tool selection; a production-grade description states purpose, inputs, example queries, edge cases, and explicit boundaries vs similar tools.

**Tool Overload Problem** — Selection reliability degrades as tool count grows; optimal range is 4-5 tools per agent, scoped to its role.

**Tool renaming** — Fixing confusingly similar tool names/purposes at the interface level without touching implementation.

**Tool splitting** — Breaking a generic, broad-responsibility tool into purpose-specific tools with defined input/output contracts.

**tool_choice** — Parameter controlling model-tool interaction: `"auto"` (model decides), `"any"` (must call a tool, picks which), or forced selection of a specific named tool.

**Transient error** — Error category for timeouts/rate limits/unavailability; the request is valid, `isRetryable: true`, retry after a brief delay.

**Validation error** — Error category for malformed/missing/out-of-range input; `isRetryable: true` only after the input itself is fixed.
