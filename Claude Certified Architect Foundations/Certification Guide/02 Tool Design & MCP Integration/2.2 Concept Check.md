
## Key Concepts

1. The MCP isError flag.
	1. The MCP protocol provides an isError flag for communicating tool failures back to the agent.
	2. Setting isError: true tells the model that tool execution failed, enabling it to reason about recovery rather than treating error text as a normal successful result.
2. The four error categories.
	1. Every tool failure falls into one of four categories, each demanding a different recovery strategy:
		1. Transient errors (timeouts, service unavailability, rate limits) - retriable after a brief delay.
		2. Validation errors (invalid input format, missing required fields) - isRetryable: false, because resending the identical call fails the same check; the agent corrects the input and sends a new one
		3. Business errors (policy violations, limit exceedances) - NOT retriable, requires alternative workflow or escalation.
		4. Permission errors (access denied, insufficient credentials) - NOT retriable, requires escalation or different credentials.
3. Structured error metadata.
	1. Each error response must include three metadata fields: `errorCategory` (transient/validation/business/permission), isRetryable (boolean), and description (human-readable explanation with recovery guidance).
	2. Without these fields, the agent cannot make appropriate recovery decisions.
4. Access failure vs valid empty result.
	1. This is the most critical distinction in this task statement.
	2. An access failure means the tool could not reach the data source (timeout, auth failure) - isError: true, the agent should consider retrying.
	3. A valid empty result means the tool successfully queried and found no matches - isError: false, the agent should NOT retry because the answer is "no results found."
	4. Confusing these two causes wasted retries and incorrect escalations.
5. Error propagation in multi-agent systems.
	1. Subagents implement local recovery for transient failures.
	2. Only propagate errors that cannot be resolved locally.
	3. Include partial results and what was attempted, so the coordinator can make informed decisions.
	4. Two anti-patterns to avoid: silently suppressing errors (returning empty results as success) and terminating entire workflows on a single failure.

## Anti-Patterns to Test

- Generic "Operation Failed" messages without structured metadata
- Retrying on valid empty results
- Treating business errors as retriable
- Silently suppressing subagent errors by returning empty results as success
- Terminating entire workflows on a single subagent failure
