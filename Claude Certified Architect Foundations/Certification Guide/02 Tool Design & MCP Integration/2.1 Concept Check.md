
## Key Concepts

1. Tool descriptions as the PRIMARY mechanism for LLM tool selection.
	1. Tool descriptions are not supplementary metadata.
	2. They are THE mechanism LLMs use to decide which tool to call.
	3. A production-grade description includes five elements: what the tool does, what inputs it expects (formats, types, constraints), example queries it handles well, edge cases and limitations, and explicit boundaries explaining when to use this tool versus similar tools.

2. The misrouting problem.
	1. Two tools with overlapping or near-identical descriptions cause selection confusion.
	2. For example, `get_customer` ("Retrieves customer information") and `lookup_order` ("Retrieves order details") with minimal descriptions cause the agent to route order-related queries to the wrong tool.
	3. When the toolkit is small enough for the agent to reason about, expanding the descriptions is the fix.

3. Count the tools before you pick the remedy.
	1. Descriptions are the fix only when the agent has a workable number of tools and simply cannot tell two of them apart.
	2. Past roughly 4-5 tools per agent, selection degrades on decision complexity alone, and rewriting 22 descriptions leaves that untouched.
	3. There the answer is Task Statement 2.3 work: split by role, or consolidate variants of one job into a parameterised tool.
	4. Few-shot examples are not a sanctioned remedy for misselection at all, and routing classifiers are keyed wrong for large tool sets.
	5. Make the student diagnose which disease they are looking at before prescribing.

4. Tool splitting.
	1.  Generic tools with broad responsibilities should be split into purpose-specific tools with defined input/output contracts.
	2. Each resulting tool has a narrow, clearly described purpose.

5. Tool renaming for clarity.
	1. Renaming tools eliminates functional overlap at the interface level.
	2. For example, renaming `analyse_content` to `extract_web_results` with a web-specific description makes purpose unambiguous without changing implementation.

6. System prompt interactions.
	1. Keyword-sensitive instructions in system prompts can create unintended tool associations that override well-written descriptions.
	2. If the system prompt says "always check customer details before proceeding", the model may associate any customer-related query with `get_customer` regardless of tool descriptions.
	3. Always review system prompts for conflicts after updating tool descriptions.
## Anti-Patterns

- Minimal descriptions like "Retrieves customer information"
- Using few-shot examples to fix misrouting caused by poor descriptions
- Building a routing classifier as a first step
- Consolidating tools as a first step
- Ignoring system prompt wording after updating tool descriptions
