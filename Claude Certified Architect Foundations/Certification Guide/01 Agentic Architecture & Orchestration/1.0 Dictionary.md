# Domain 01 Dictionary — Agentic Architecture & Orchestration

**--resume \<session-name\>** — CLI option that continues a specific named session, restoring its full conversation history including all prior tool results. Only works on sessions that already exist.

**-c / --continue** — Resumes the most recent conversation in the current directory without needing a session name.

**Agentic Loop** — The core, deterministic execution cycle behind every Claude-based agent: send a request → inspect `stop_reason` → execute tools if needed → repeat until `end_turn`.

**AgentDefinition** — The object that defines a subagent: its description, system prompt, and tool restrictions.

**allowedTools** — Configuration list of tools an agent may call. The coordinator's `allowedTools` must include `"Task"` or `"Agent"` or it cannot spawn subagents at all.

**AML check** — Anti-money laundering compliance check; example of a prerequisite gate used to block `transfer_funds` until satisfied.

**Attention Dilution** — Failure mode where an agent processes too many items in one pass, producing inconsistent depth (thorough on early items, shallow on later ones). Fixed by multi-pass architecture, not a bigger model or context window.

**Coordinator agent** — The central node in a hub-and-spoke multi-agent system; decomposes tasks, invokes subagents, aggregates results, and is the only thing subagents talk to.

**Critical Isolation Principle** — Subagents do NOT automatically inherit the coordinator's conversation history, system prompt, or other subagents' results, and share no memory between invocations; every invocation is independent and starts with only what the coordinator explicitly puts in its prompt.

**Cross-item integration pass** — The second layer of a multi-pass architecture; runs after all per-item passes to catch relationships and inconsistencies across items.

**Dynamic Adaptive Decomposition** — Task decomposition pattern where subtasks are generated based on what's discovered as the agent goes; best for open-ended, unknown-scope work (e.g. legacy codebase exploration).

**Dynamic subagent selection** — Coordinator responsibility: analysing query requirements and choosing which subagents to invoke rather than always routing through the full pipeline (e.g. a simple factual question may only need the web search subagent).

**end_turn** — The `stop_reason` value signalling Claude has finished its work and the agentic loop should terminate.

**Fixed Sequential Pipeline (Prompt Chaining)** — Task decomposition pattern using predetermined steps in a fixed order; best for predictable, structured tasks (e.g. document extraction) but cannot adapt to unexpected findings.

**fork_session** — Creates an independent branch from a shared analysis baseline for exploring divergent approaches; branches don't see each other's results. Distinct from `--resume` (continuation, not divergence).

**Fresh start with summary injection** — Session management option: start a new session and inject a structured summary of prior findings, avoiding stale tool results. Correct fix for the stale context problem.

**Hub-and-Spoke Architecture** — Multi-agent architecture where all communication flows through a central coordinator; subagents never talk to each other directly.

**Iterative refinement loops** — Coordinator responsibility: evaluating synthesis output for gaps and re-delegating to search/analysis subagents with targeted queries until coverage is sufficient — not a single-shot process.

**Manager approval workflow** — Example of a PreToolUse hook use case: pausing execution above a threshold (e.g. >20% discount) and routing to a human approval queue.

**Model-Driven Decision-Making** — Claude choosing which tool to call from context, as opposed to pre-configured decision trees or fixed sequences.

**Multi-Concern Request Handling** — Correct pattern for compound customer requests: decompose into distinct items, investigate in parallel with shared context, synthesize one unified response.

**Multi-pass architecture** — Fix for attention dilution: split work into per-item local analysis passes plus a separate cross-item integration pass.

**Narrow Decomposition Failure** — Exam pattern where a coordinator's task decomposition misses entire categories of scope (not depth); root cause traces to the coordinator, not the subagents.

**Parallel spawning** — Emitting multiple Task/Agent tool calls in a single coordinator response to invoke independent subagents simultaneously, reducing latency versus sequential invocation.

**Per-item local analysis pass** — First layer of multi-pass architecture; each item (file, document, module) gets its own pass with full attention.

**PostToolUse hook** — Runs after a tool executes but before the model sees the result; used to transform/normalise data. Cannot block actions — the tool has already run.

**Prerequisite gate** — A programmatic check that physically blocks a tool from executing until a prior condition is met (e.g. `process_refund` blocked until `get_customer` returns a verified ID).

**PreToolUse hook** — Runs before a tool executes; can block, modify, or redirect the outgoing call. The correct mechanism for enforcing policy (e.g. refund thresholds, AML checks).

**Programmatic enforcement** — Deterministic control via hooks/gates/code-level checks; required whenever a single failure would cause financial loss, security breach, or compliance violation.

**Prompt-based guidance** — Instructions placed in the system prompt; probabilistic (works ~90-95% of the time), acceptable only for low-stakes operations.

**Research scope partitioning** — Coordinator responsibility: assigning distinct subtopics/source types to different subagents to minimise duplication.

**Session State and Resumption** — Domain topic covering the three session-management options: `--resume`, `fork_session`, and fresh start with summary injection.

**Stale Context Problem** — Occurs when a resumed session reasons from cached tool results (e.g. old file contents) that no longer reflect the current state after files changed.

**stop_reason** — Field in the Claude API response that is the sole authoritative signal for agentic loop control; values include `tool_use` and `end_turn`.

**Structured Handoff Protocol** — Required format for escalating to a human agent: must be self-contained (customer ID, conversation summary, root cause, refund amount, recommended action) since the human has no access to the transcript.

**Structured metadata format** — Data format for inter-agent context passing that separates content (claim/fact) from metadata (source URL, document name, page number) so downstream agents can attribute claims.

**SubagentStart** — Lifecycle hook that fires when a subagent is spawned via the Task tool; observational only (can log/inject context, cannot block).

**Subagent-scoped hooks** — PreToolUse/PostToolUse hooks defined in a subagent's own `AgentDefinition` frontmatter; scoped only to that subagent's tool calls.

**SubagentStop** — Lifecycle hook that fires when a subagent finishes; can return `decision: "block"` to send the subagent back to keep working, but cannot transform its output.

**Stop hook auto-conversion** — Stop hooks defined in a subagent's frontmatter are automatically converted to `SubagentStop` events at runtime.

**Targeted Re-Analysis** — Re-analysing only the specific files that changed since a prior session, rather than the whole codebase, when starting fresh with summary injection.

**Task Decomposition** — Breaking complex work into pieces an agentic system can handle; two main patterns are fixed sequential pipelines and dynamic adaptive decomposition.

**Task tool (Agent tool)** — The API mechanism by which a coordinator spawns subagents. Renamed `Agent` in current Claude Code; `Task` still works as an alias.

**tool_use** — The `stop_reason` value indicating Claude wants to call one or more tools; the agentic loop continues.
