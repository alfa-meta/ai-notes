# Domain 03 Dictionary — Claude Code Configuration & Workflows

**-p / --print flag** — Runs Claude Code non-interactively for CI/CD: processes the prompt, outputs to stdout, and exits. Without it, a CI job hangs waiting for input. The single most directly tested fact in this domain.

**--add-dir \<path\>** — Grants Claude access to an additional directory for reading/editing (not configuration discovery).

**--allowedTools / --disallowedTools / --tools** — CLI flags scoping which tools run without a permission prompt, which are denied, or which built-in tools are available at all.

**--append-system-prompt(-file)** — Appends text or a file's contents to the default system prompt, keeping Claude Code's default tool guidance while adding extra rules.

**--bare** — Minimal startup mode: skips auto-discovery of hooks, skills, plugins, MCP servers, auto memory, and CLAUDE.md, leaving only Bash/file tools, for fast predictable scripted runs.

**--input-format text|stream-json** — Controls input shape for `-p`.

**--json-schema** — Print-mode flag that validates the agent's final output against a JSON Schema; the result lands in the JSON envelope's `structured_output` field.

**--max-turns** — Caps the number of agentic turns before exiting.

**--model \<alias|name\>** — Sets the session model (e.g. `sonnet`, `opus`).

**--output-format text|json|stream-json** — Controls output shape for `-p`; `json`/`stream-json` are machine-parseable.

**--permission-mode** — Sets startup permission mode: `default`, `acceptEdits`, `plan`, `auto`, `dontAsk`, or `bypassPermissions`.

**--system-prompt(-file)** — Replaces the entire default system prompt with text or a file's contents (vs the append variants).

**--verbose** — Full turn-by-turn output flag.

**-c / --continue, -r / --resume** — Resume the most recent conversation in the current directory, or a specific named/ID'd session.

**/compact** — Command that summarises a long session; project-root CLAUDE.md survives it because Claude re-reads it from disk, not because it's privileged.

**/memory** — Diagnostic command that shows which memory/config files are currently loaded; does not itself load anything.

**@ path imports** — `@<path>` syntax in CLAUDE.md that inlines another file's content at load time; loads eagerly, so splitting a file doesn't shrink the context Claude actually sees.

**.claude/rules/** — Directory of topic-specific rule files, optionally scoped with `paths:` frontmatter so they load only for matching files — the token-efficient alternative to a giant root CLAUDE.md.

**.claude/skills/ (SKILL.md)** — Canonical, fuller-featured location for a `/command`: a directory per skill containing a required `SKILL.md` entrypoint; supports frontmatter, auto-discovery, and wins on name collision with `.claude/commands/`.

**.claude/commands/** — Flat-file alias for creating `/commands`; still works for backward compatibility but lacks the skills system's extra features.

**allowed-tools (frontmatter)** — Skill/command frontmatter that pre-approves listed tools to run without a permission prompt while that skill is active; doesn't restrict other tools.

**argument-hint (frontmatter)** — Skill/command frontmatter that prompts the developer for required parameters when invoked without arguments.

**Batch vs sequential feedback** — Refinement rule: deliver interacting fixes in a single batched message; deliver independent issues sequentially, one iteration at a time.

**CI/CD Integration** — Domain topic covering running Claude Code non-interactively, with structured, machine-parseable, session-isolated output.

**CLAUDE.local.md** — Personal, gitignored-by-convention companion to CLAUDE.md at any hierarchy level; loads after CLAUDE.md (load order, not precedence).

**CLAUDE.md** — Configuration file loaded at user, project, and directory levels; files are concatenated into context (not overriding each other), and conflicts may resolve arbitrarily — it's guidance, not a hard enforcement layer.

**Concrete input/output examples** — Most effective refinement technique when prose descriptions produce inconsistent interpretation; 2-3 examples set the pattern.

**context: fork (frontmatter)** — Skill frontmatter that runs the skill in an isolated sub-agent context so verbose output doesn't pollute the main conversation.

**Direct execution** — Mode for well-scoped changes with a known approach and limited scope (single-file bug fix, known config change); skips the planning phase.

**Directory-level CLAUDE.md** — Applies only to one specific subdirectory; wrong tool for conventions spanning many directories (use path-specific rules instead).

**Explore subagent** — Runs codebase discovery in isolation and returns only summaries, keeping the main conversation's context window clean during multi-phase tasks.

**Incremental review context** — Feeding prior review findings into each new CI review run and instructing Claude to report only new or still-unaddressed issues, so a fixed issue drops off and an ignored one isn't re-flagged every push — prevents duplicate comments eroding developer trust.

**Interview pattern** — Refinement technique for unfamiliar domains: have Claude ask clarifying questions before implementing, surfacing considerations the developer might miss.

**Message Batches API (CI use)** — 50% cheaper, up to 24hr processing, no latency SLA; correct only for non-blocking workflows (overnight/weekly reports), never for blocking pre-merge checks.

**Path-specific rules (paths: frontmatter)** — `.claude/rules/` files scoped by glob pattern so conventions for one file type (e.g. `**/*.test.tsx`) apply automatically across every matching directory without duplication.

**Plan mode** — Mode for complex tasks needing exploration, multiple valid approaches, architectural decisions, or multi-file changes; explores/proposes without modifying files.

**Plan-then-execute (hybrid)** — Common tested pattern: use plan mode to investigate and design, then switch to direct execution to implement the already-decided approach.

**Project-level config** — `.claude/CLAUDE.md` or root `CLAUDE.md`; version-controlled, applies to every team member who clones the repo.

**Session context isolation (CI review)** — The same session that generated code is a weaker reviewer of it (retains justification bias); use an independent Claude Code invocation for review.

**settings.json** — Has a strict precedence chain (managed policy > local > project > user) and is enforced by the client regardless of what Claude decides — the correct place for rules that must hold every time, unlike CLAUDE.md.

**Skills system** — Unified system merging custom commands and skills; both `.claude/skills/` and `.claude/commands/` produce the same `/command` and support the same frontmatter (`context: fork`, `allowed-tools`, `argument-hint`), but only skills add a supporting-files directory, automatic discovery, and precedence on a name collision.

**structured_output field** — Where schema-validated data lands inside the `--output-format json` envelope when `--json-schema` is used.

**Test-driven iteration** — Most effective refinement technique for complex transformations: write tests first, then feed Claude the concrete failure output.

**User-level config** — `~/.claude/CLAUDE.md`; personal, not version-controlled, never shared via git — root cause of the "new team member gets different behaviour" exam scenario when team rules live here by mistake.
