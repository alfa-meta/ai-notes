
## Key Concepts

1. Unified Skills System:
	1. Commands and skills have been merged, and both paths create identical /commands, but their file structures differ.
	2. A skill is a DIRECTORY containing a SKILL.md file (.claude/skills/deploy/SKILL.md), the directory name becomes the command name.
	3. A command is a FLAT Markdown file (.claude/commands/deploy.md), the filename becomes the command name.
	4. A flat file placed directly inside ./claude/skills/ does NOT create a command.
	5. .claude/skills/ is the canonical location.
	6. .claude/commands/ remains supported for backward compatibility.
2. Project-scoped commands: stored inside the repository, as .claude/skills/`<name>`/SKILL.md or .claude/commands/`<name>.md`.
	1. Version-controlled, shared via git.
	2. Every developer gets them on clone/pull
	3. Use for team-wide workflows like /review, /deploy-check, /lint
3. User-scoped commands: stored in the home directory, as ~/.claude/skills/`<name>`/SKILL.md or ~/.claude/commands/`<name>`.
	1. Personal, NOT version-controlled, NOT shared via git.
	2. Use for individual productivity workflows that do not need team standardisation.
4. SKILL.md files in .claude/skills/ support optional frontmatter configuration (context: fork, allowed-tools, argument-hint).
	1. Skills are on-demand, task-specific workflows invoked when needed.
	2. NOT loaded automatically like CLAUDE.md.
5. context: fork frontmatter: runs the skill in an isolated sub-agent context.
	1. Verbose output stays contained.
	2. The main conversation remains clean.
	3. Essential for codebase analysis, brainstorming, and anything producing noisy output.
	4. Without it, skill output fills the context window and degrades subsequent responses.
6. allowed-tools frontmatter: the exam guide describes this as restricting the skill's tool access, and that is the expected exam answer.
	1. In current Claude Code it pre-approves the listed tools so the run without a permission prompt; disallowed-tools is the actual security boundary.
	2. Either way, a read-only analysis skill should not be using Write or Bash.
7. argument-hint frontmatter: prompts the developer for required parameters when the skill is invoked without arguments.
8. Skills vs CLAUDE.md critical distinction:
	1. Skills = on-demand, task-specific workflows (invoked when needed)
	2. CLAUDE.md = always-loaded, universal standards (applied automatically)
	3. Never put task-specific procedures in CLAUDE.md
	4. Never put universal standards in skills
9. Personal skill customisation: create personal variants in ~./.claude/skills/ with different names to avoid affecting teammates.

## Anti-Patterns

1. Putting task-specific procedures in CLAUDE.md instead of skills
2. Putting universal standards in skills instead of CLAUDE.md
3. Not using context: fork for verbose/exploratory skills
4. Placing team-shared commands in user-scoped paths (~/.claude/commands/ or ~/.claude/skills/) instead of project-scoped paths (.claude/commands/ or .claude/skills/)
5. Leaving destructive tool access open for skills that should be read-only (list safe tools in allowed-tools; the hard boundary in current Claude Code is disallowed-tools)


## Exam Traps

1. The file structures are NOT interchangeable: skills are directories with a SKILL.md entrypoint; flat .md files belong in .claude/commands/. 
	1. If the student (or an answer option) describes a flat file directly inside .claude/skills/, such as .claude/skills/review.md, correct it: that file does not create a command.
2. .claude/commands/ and .claude/skills/ are both project-scoped (shared via git) and create the same /commands.
	1. ~/.claude/commands/ and ~/.claude/skills/ are both user-scoped (personal).
	2. When a command needs to be available to everyone, the answer is always a project-scoped path.
3. Skills are on-demand. They must be explicitly invoked. CLAUDE.md loads automatically.
	1. If the exam asks about automatic application of conventions, the answer is CLAUDE.md or .claude/rules/, not skills.
4. context: fork isolates verbose skill output from the main conversation.
	1. Without it, brainstorming or analysis output pollutes the context window.
