
Tool - is a function an agent can call, with a name and a plain-language descriptions.
	Tool descriptions are the primary mechanism LLMs use for tool selection.
	Given a set of tools, the model reads them to decide which one to call.
	They are not supplementary metadata.
	Minimal descriptions, such as "Retrieves customer information", leave the model no way to tell apart overlapping tools.


## What Makes a Good Tool Description

A production-grade tool description includes five elements.
1. What the tool does: its primary purpose, stated unambiguously.
2. What inputs it expects: data types, formats, constraints, and required versus optional fields.
3. Example queries it handles well: concrete use cases that anchor the model's understanding
4. Edge cases and limitations: what the tool does not do, and what happens when inputs fall outside expected ranges.
5. Explicit boundaries: when to use this tool versus similar tools in the same toolkit.

## Misrouting problem

Two tools with overlapping or near-identical descriptions cause selection confusion.
Both fit the request, so nothing points the model to the right one.
Expand both descriptions with the five elements.


## Tool Splitting

Generic tools with broad responsibilities create ambiguity, because a broad description fits many requests.
Split them into purpose-specific tools with defined input and output contracts.


Each resulting tool does one narrow, clearly described job the model can match to the user's need.


## Tool Renaming for Clarity

When two tools have confusingly similar names, renaming fixes the overlap at the interface level.
Rename `analyze_content` to `extract_web_results` with a web-specific description, and its purpose becomes unambiguous without touching its implementation.


## System Prompt Interactions

Keyword-sensitive instructions in system prompts can create unintended tool associations that override well-written descriptions.
Told to "always check customer details before proceeding", the model may route any customer-related query to `get_customer`, whatever the descriptions say.
After updating descriptions, reread your system prompt for conflicts , a subtle failure mode.


## Exam Tips

The exam consistently favours low-effort fixes with a large effect: better descriptions before routing classifiers, scoped access before full access, community servers before custom builds.
System prompt conflicts are tested too.


### Key Concept

When weak descriptions cause misrouting, improving them is the first fix.



## Exam Traps


### Choosing few-shot examples to fix tool misrouting caused by minimal descriptions

Few-shot examples add token overhead without addressing the root cause.
The model is confused because descriptions do not differentiate the tools - fix the descriptions first.

### Implementing a routing classifier as the first step to fix tool selection

A routing classifier is over-engineered as a first response.
It bypasses the LLM's natural language understanding and adds infrastructure the exam does not consider proportionate.

### Consolidating similar tools into one as the first step

Tool consolidation is a valid long-term architectural choice, but it requires more effort than expanding descriptions.
The exam favours low-effort, high-leverage first steps.

### Ignoring system prompt wording after updating tool descriptions

Keyword-sensitive instructions in system prompts can silently override well-written tool descriptions, creating unintended tool associations.
