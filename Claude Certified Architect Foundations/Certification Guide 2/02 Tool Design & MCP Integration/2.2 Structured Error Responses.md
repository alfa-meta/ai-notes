
Structured Error Response - is the result an MCP tool returns when a call fails.
	Its metadata tells the agent the error's category, whether a retry can work, and how to recover.
	The MCP protocol provides the `isError` flag to report the failure to the agent.
	With it set, the model knows the execution failed and reasons about recovery, instead of reading the error text as a normal successful result.
	This response decides whether the agent recovers intelligently or fails blindly.
	A generic message such as "Operation failed" is useless to an LLM, because it says nothing about what went wrong, whether to retry, or what to try instead.


Protocol Errors - are standard JSON-RPC error responses.
	The server sends one when the request itself is malformed.
	The tool name does not exist, the arguments fail the input schema, or the server hits an internal fault.
	There is no result object, only an `error` with a `code` and a `message`.
	The host application handles these.
	The model never sees a tool result, because no tool ran.
	A misspelt tool name from the framer's agent would fail here.


Tool Execution Errors - are results.
	The tool was found, the arguments were valid and the tool ran.
	Then something went wrong inside it: an upstream API failed, the input data was wrong, or a business rule rejected the request.
	The server returns a normal result with `isError: true` and the detail in `content`.
	The model reads it and decides what to do next.
	A failed stock check at the framer would be one.

The four categories, `isRetryable` and the recovery guidance all describe execution errors, because that is the layer the agent reasons about.
A protocol error means the call was built wrong.
The fix belongs in the tool schema or the client, not in the agent's recovery loop.


## The Four Error Categories

1. Transient Errors - Timeouts, service unavailability, rate limits. The underlying system is briefly unreachable, but the request is valid.
	1. Recovery: Retry after a short delay
2. Validation Errors - Invalid input format, missing required fields, out-of-range values. The request itself is malformed.
	1. Recovery: fix the input, then send a corrected call.
3. Business Errors - Policy violations, limit exceedances, business rule conflicts.
	1. The request is technically valid but breaks a business constraint.
	2. Recovery: do not retry. The agent needs an alternative workflow.
4. Permissions Errors - Access denied, insufficient credentials, authorisation failures.
	1. The tool cannot run because the caller lacks the required permissions.
	2. Recovery: escalate or use different credentials.

## What `isRetryable` Signals

`isRetryable` answers one narrow question: will resending this exact request work?
Only transient errors get `true`, because the call was valid and the system was briefly unavailable.
Every other category get `false`, because something has to change first: the input (validation), the request itself (business) or the other caller (permission)

## Access Failure vs Valid Empty result

Access Failure - means the tool could not reach the data source.
	A timeout occurred, authentication failed, or the service was down.
	The data might exists, but the tool could not check.


Valid Empty Result - means the tool queried the data source successfully and found no matches,
	The query ran correctly, and no data matches the criteria.
	The agent should not retry.
	The answer is "no results found".

A tool should distinguish the two: an access failure needs a retry decision, and a valid empty result is a successful query with no matches.

## Error Propagation in Multi-Agent Systems

In Multi-agent systems, error handling follows a principle of local recovery with selective propagation.
Say the framer's coordinator sends a subagent to compare moulding prices from five suppliers.
1. Subagents implement local recovery for transient failures. If one supplier's price list times out, the subagent retries before bothering the coordinator.
2. Only propagate errors that cannot be resolved locally. If all retries fail, the subagent reports the failure upward.
3. Include partial results and what was attempted. The coordinator needs context: "I checked 3 of 5 suppliers successfully. Suppliers 4 and 5 timed out. Here are partial results from the 3 that answered."


## Exam Traps


### Retrying when a tool returns an empty result from a successful query

An empty result from a successful query means 'no data matches your criteria.'
Retrying will produce the same empty result.
The agent should accept the result and respond accordingly.
### Using generic error messages like 'Operation failed' without structured metadata

Without `errorCategory`, `isRetryable`, and a descriptions, the agent cannot distinguish transient failures from a business rule violations.
### Treating business errors as retryable

Business errors will never resolve through retry.
The same policy violation applies every time.
The agent must take an alternative path such as escalation.

### Marking a validation error isRetryable: true because the agent can recover from it

isRetryable asks whether resending this exact call can work.
A malformed order ID fails the same check every time, so validation is isRetryable: false.
The agent recovers by correcting the input and issuing a new call, which `errorCategory` conveys.

### Reading isRetryable: false as 'abandon the task'

Validation is false because the input must change first, and the agent fixes it unaided.
Business and permission errors still continue, through an alternative path, escalation or a different principal.
None of the three non-retryable categories means abandon the task.

### Silently suppressing subagent errors by returning empty results as success

Returning empty results as success hides the failure, so the coordinator cannot tell 'found nothing' from 'could not search'.
Return structured error context instead, with the failure type, the attempted query and any partial results.
